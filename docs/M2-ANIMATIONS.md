# M2 Animation Reference - ids, names, and what this client does with them

Everything here is measured from this repo's own data, not assumed. Where a claim came from the
wowdev.wiki animation list it is marked as such; where it came from decoding the shipped tables it is
marked with the file it came from.

Primary external reference, and the reason modern mounts are workable at all:

- **<https://wowdev.wiki/M2/AnimationList>** - the official animation id -> name table.
  1778 named ids, range `0..1777`. Cached locally at `analysis/animlist.txt`
  (generated by `analysis/parse_animlist.py` from `analysis/animlist.html`).

---

## 1. Where animation ids come from

An M2 file carries a **sequence table**. Each sequence has an `id`, a `duration`, a `moveSpeed` and
`flags`. The id is the animation (see the wiki list). A model author only the ids it needs, and its
numbering is not fixed - a 3.3.5a creature and a retail mount can use completely different numbers for
the same movement.

Structural facts confirmed the hard way:

| fact | value |
|---|---|
| `M2Sequence` stride | `0x40` |
| `M2Sequence` layout | `id u16 @0x00`, `variation u16 @0x02`, `duration u32 @0x04`, `moveSpeed f32 @0x08`, `flags u32 @0x0C` |
| sequence array header in `M2Data` | offset `0x1C` (count at `0x1C`, offset at `0x20`) |
| sequence array in a raw MD20 file | count at `0x28`, offset at `0x2C` |
| array offsets | **absolute file offsets**, not relative to the MD20 body |
| `MD21` container | fourcc `MD21`, `u32` length at `+4`, embedded `MD20` starts at `+8` |

Getting the `0x28`/`0x1C` and `0x40`/`0x44` choices wrong produces *plausible-looking* garbage
(ids in the tens of thousands, nonsense durations) rather than an error. Always sanity-check that the
first entries look like small, sensible animation ids.

## 2. AnimationData: the table that gives ids meaning

`DBFilesClient\AnimationData.db2` is **not** a supplement to `AnimationData.dbc` - it is the same table
at a later revision, and it covers every stock id as well. **1866 rows, ids `0..1865`.**

The stock 3.3.5a `AnimationData.dbc` stops at id **505**. `WowClientDB::GetRecord` is a minId/maxId range
check, so any id past that returns `null`: no behaviour, no fallback, no animation. That single fact is
why retail mounts could not animate at all before the db2 was wired in.

### Columns

Four physical fields, shapes **`1 1 1 2`** (three scalars and one two-element array):

| field | meaning |
|---|---|
| `f0` | fallback id - the next id to try if this one is absent |
| `f1` | behaviour tier - `0` = untiered/base, `3` = flight tier |
| `f2` | behaviour id - *what movement this animation is* |
| `f3` | flags (2 elements) |

> The shapes are `1 1 1 2`. Reading them as `1 1 2 2` consumes 12 bits too many per row and runs the bit
> reader out inside the pallet index, which reports as `WDC5: invalid pallet-array index` - a message that
> says nothing about the real cause.

### Reading it

```
ModernAssetsTest animdb2 <file.db2> 1 1 1 2 [id ...]
```

Output is UTF-16LE. Decode with `encoding='utf-16'` if parsing it in Python.

## 3. How a movement is identified

**Behaviour id is the movement. Tier is the context.**

At tier 0, behaviour 42 is *swim forward*. At tier 3, behaviour 42 is *fly-swim forward* - the same
movement in a different context. This is the key that unlocks everything below.

The stock flight block is contiguous: **ids `229..485`, tier 3, behaviour = `id - 229`**.

| id | behaviour | official name | role |
|---|---|---|---|
| 229 | 0 | `FlyStand` | hover |
| 232 | 3 | `FlyStop` | hover |
| 233 | 4 | `FlyWalk` | walk |
| 234 | 5 | `FlyRun` | forward |
| 240 | 11 | `FlyShuffleLeft` | turn |
| 241 | 12 | `FlyShuffleRight` | turn |
| 271 | 42 | `FlySwim` | forward |
| 272 | 43 | `FlySwimLeft` | left |
| 273 | 44 | `FlySwimRight` | right |
| 274 | 45 | `FlySwimBackwards` | backward |
| 321 | 92 | **`FlyRunRight`** | right |
| 322 | 93 | **`FlyRunLeft`** | left |
| 364 | 135 | `FlyFly` | wing-cycle |
| 550 | - | **`MountFlightBackwards`** | backward |

> `321` is *Right* and `322` is *Left*. I had these swapped for several attempts; the wiki settles it.

### Retail "advanced flying" block

Retail mounts carry a second, newer vocabulary. These are the clips that actually look good:

| id | name | role |
|---|---|---|
| 1532 | `AdvFlyForwardGlide` | **forward (glide)** |
| 1722 | `AdvFlyForwardGlideSlow` | forward (slower glide) |
| 1724 | `AdvFlyForwardGlideFast` | forward (faster glide) |
| 1520 | `AdvFlyLeft` | left |
| 1522 | `AdvFlyRight` | right |
| 1558 | `AdvFlyRollEnd` | forward-ish |
| 1638 | `AdvFlyFlap` | **one-shot flap** |
| 1680 | `AdvFlyFlapBig` | one-shot flap |
| 1702 | `AdvFlyFlapUp` | one-shot flap |
| 1706 | `AdvFlyFlapFoward` | one-shot flap |
| 1726 | `AdvFlySecondFlapUp` | one-shot flap |
| 1530 | `AdvFlyDown` | descend |
| 1704 | `AdvFlySlowFall` | descend |
| 1678 | `AdvFlyDownStart` | descend |

**The flap ids are events, not loops.** `1706`/`1680`/`1702`/`1726`/`1638` play through once and stop.
Using one as the sustained air animation is why a mount gives a single wingbeat and then freezes.
The looping clips are `1532`/`1722`/`1724`.

## 4. Resolving a role for an arbitrary model

A model's own id numbers mean nothing; its **fallback chain** does. Two signals, both read from the
model itself, in this order:

1. **The AdvFly block.** If the model carries any of `1532`/`1722`/`1520`/`1522`/`1702`/`1530`, it is a
   retail flier and those ids supply forward/left/right directly.
2. **The fallback chain.** Otherwise take the model's own id whose chain reaches a stock id with the
   wanted role, **in the fewest hops**.

Fewest-hops matters. `509` is `FlyAttackFist1H` and its chain passes through `FlyStand`; ranking by
id size or by "is it modern" lets a *spell* animation win the hover role over `FlyStand` itself.

### Measured coverage (26 mounts harvested from a live session)

| role | coverage | example ids |
|---|---|---|
| hover | 12/26 | `229`, `509`, `280` |
| walk | 12/26 | `233`, `242` |
| forward | 11/26 | `234`, `1558` |
| left | 12/26 | `322`, `1520` |
| right | 12/26 | `321`, `1522` |
| **backward** | **19/26** | `550`, `1146` |
| glide | 13/26 | `1532`, `1724` |
| flap | 4/26 | `1638`, `1680`, `1706` |

Every mount has *some* backward clip. No mount has a flight-tier strafe distinct from left/right -
`321`/`322` **are** the lateral flight clips.

## 5. The wing-beat

A retail flier's forward clip is a glide. Played alone the mount never beats its wings and reads as
dead. The `wxl-mana-speedflying` module solves this with a **level beat**, and that shape is what this
client uses:

- hold the glide (`1532`);
- every **4000-8000 ms** (randomised, xorshift - no seeding to get wrong) play a one-shot flap through
  once, held for its own recorded duration;
- return to the glide.

Reference defaults: `LevelBeatMinMs=4000`, `LevelBeatMaxMs=8000`, `LevelBeatBlendMs=450`.

Only forward travel is punctuated. Hover already loops a standing clip; a strafe or reverse is a short
deliberate move whose own clip should not be interrupted.

## 6. Pitfalls that cost real time

Recorded so they are not repeated.

| symptom | real cause |
|---|---|
| `invalid pallet-array index` | wrong column shapes (`1 1 2 2` instead of `1 1 1 2`) |
| offline tool decodes fine, client fails on identical bytes | the tool read its arguments from the wrong `argv` index and silently tested a different layout |
| mount plays one wingbeat then freezes | a one-shot flap id used as the sustained clip |
| mount glides forever and never flaps | the glide used without a level-beat layer |
| "glide" that looks slightly wrong | `1532 -> 1524 -> 42` **SWIM**; at that point it was a swim loop |
| mount swims sideways | stock `43/44/45` were used, which are tier-0 swim |
| mount never changes animation while moving | the mount branch was gated on `IsFullBodyAnim(rider's anim)`, and a mounted player picks `ANIM_SWIM` in the air, which that predicate rejects |
| run animation loops after stopping | `ChooseMovementAnim` returned "handled" without writing `*anim`, so the caller's `ANIM_COUNT` seed propagated |
| crash in `CM2SceneRender::DrawBatch` | `M2Array` stores a 32-bit delta from its own address; a heap allocation >2 GiB from the mapped body truncates. Fixed by keeping the repacked pointer out-of-band |
| T-pose that "clearing the cache fixes" | the same truncated pointer - whether it landed in range was allocator luck |

## 7. Tooling in this repo

| tool | purpose |
|---|---|
| `ModernAssetsTest animdb2 <db2> 1 1 1 2 [ids]` | decode AnimationData and print every field per row |
| `ModernAssetsTest m2 <file.m2>` | repack a modern model and report the conversion |

The reliable way to harvest what a mount really carries is the temporary dump in
`CM2Shared::Initialize` (`Logs\m2-sequences.csv`): it writes every parsed sequence, as the **engine**
parsed it, for every model the client loads. Scroll the mount journal once and you have the whole set.
